# Data Architecture

> Source: V2 DOCS Phase 3 Prompt 7 — data architecture. Defines the storage role of
> each backing technology referenced in `docs/architecture/system-architecture.md` §1.

## 1. PostgreSQL — System of Record

- One logical database per deployment; one schema per service
  (`auth.*`, `event.*`, `order.*`, ...) within a shared instance for Phase 1
  (modular monolith), allowing extraction to per-service databases later
  without changing application code (no cross-schema FKs, per
  `domain-model.md` §10).
- Every tenant-scoped table carries `tenant_id` (indexed, leading column on
  composite indexes) — see `security-model.md` §3 for isolation enforcement.
- Each service schema includes an `outbox` table:

  | Column | Type | Notes |
  |---|---|---|
  | `id` | uuid | event_id |
  | `event_type` | text | e.g. `order.paid` |
  | `tenant_id` | uuid | |
  | `payload` | jsonb | |
  | `created_at` | timestamptz | |
  | `dispatched_at` | timestamptz, nullable | set by relay |

- Migrations: one migration set per service schema, versioned independently.

## 2. Redis — Cache, Locks, Idempotency

Used by `infra/cache`, consumed by multiple services for:

| Use case | Key pattern | TTL |
|---|---|---|
| Idempotency (`api-standards.md` §7) | `idem:{tenant_id}:{key}` | 24h |
| Inventory reservation holds | `inv:{pool_id}:{order_id}` | configurable (e.g. 10 min) |
| Rate limiting (`api-standards.md` §6) | `ratelimit:{tenant_id}:{route_group}` | 1 min sliding window |
| RBAC permission cache | `perm:{user_id}` | invalidated on `role.assigned/revoked` |
| Session/refresh-token denylist | `revoked:{token_id}` | token TTL |

## 3. Kafka — Event Streaming

- Topics per `event-catalog.md`, partitioned by `tenant_id` (ensures
  per-tenant event ordering).
- Outbox relay (`infra/event-bus`) polls each service's `outbox` table and
  publishes to Kafka, marking `dispatched_at`.
- Consumer groups: one per consuming service per topic; offsets committed only
  after successful, idempotent processing.
- Retention: domain topics retained 7-30 days (replay window for new
  consumers/read-model rebuilds); audit-relevant topics may be retained longer
  per tenant compliance tier.

## 4. OpenSearch — Search & Discovery

- Indices: `events`, `sessions`, `speakers`, `attendees` (owned by `search`,
  per `service-map.md`).
- Populated/updated via Kafka consumers (`event.*`, `session.*`, `speaker.*`,
  `attendee.*`).
- Index documents are tenant-scoped via a `tenant_id` field with a filter
  applied on every query (defense in depth alongside application-level
  tenant checks).
- Augmented with vector fields (`embedding`) for semantic/hybrid search,
  populated via `embedding.updated` from `ai-service`.

## 5. Object Storage (S3-compatible)

| Bucket/prefix | Contents | Written by |
|---|---|---|
| `badges/{tenant_id}/{event_id}/` | generated badge PDFs/QR images | onsite |
| `exports/{tenant_id}/` | analytics CSV/JSON exports | analytics |
| `assets/{tenant_id}/` | tenant branding, design assets | tenant, design system |
| `attachments/{tenant_id}/{event_id}/` | session materials, exhibitor docs | agenda, exhibitor |

- Access via signed URLs (time-limited), generated by the owning service —
  object storage is never exposed directly to `apps/web`.

## 6. Data Lifecycle

- **Archival**: on `event.archived`, write-side tables remain queryable
  read-only; read models retained for reporting per tenant plan.
- **Tenant offboarding**: cascading export + soft-delete across all schemas
  keyed by `tenant_id`, executed via `platform_admin` tooling
  (`security-model.md` §4).
- **Backups**: PostgreSQL point-in-time recovery (infra-level, `infra/deployment`);
  Kafka and Redis are not durable stores of record — all durable state lives in
  PostgreSQL or object storage.
